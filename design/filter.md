# Filter law and resonance

The filter is a four-pole ladder with a soft-clipped feedback path. I've kept the
ladder in the end because the IR3109's implicit circuit solve at 176.4 kHz does
not fit the 24-voice budget, so the current filter is based on numbers from the reference that are supposed to give the SH101's general feel: the exponential cutoff, the linear resonance slider, the bass
thinning and the input saturation.

I wrote this note after some empirical testing and reading through the Lemus SH-101
model, because the old filter had a linear coefficient and never
self-oscillated, which I guess is a polite way of saying it didn't quite do what it was supposed to.

## Reference

The reference is the Lemus SH-101 model at tag `ro-mono-101-v0.1.3`, files
`machines/sh101/core/filter.{h,cpp}` and
`machines/sh101/core/vcf_ir3109.{h,cpp}`. Its `docs/model-filter.md` gives the following behaviour measurements:

- FREQ covers about 12 octaves. The real unit runs from about 3.5 Hz to 14.7 kHz
  and Roland's from about 3.4 Hz to 15.6 kHz. The law is exponential below
  10 kHz and compresses above it.
- The resonance pot is a linear B taper. Self-oscillation starts at VR18 about
  0.79 to 0.82, and the feedback loop's diodes bound the amplitude.
- The ENV depth at maximum is about 7.0 to 7.65 octaves.

The phase splitter took a bit of retinkering because it turns out TR26 and TR27 do two
jobs at once on the original circuit: the inverted path feeds the resonance loop through R129 and the
diodes, whilst the non-inverted path goes forward into the output sum, and that
output sum is what the `comp` default is trying to match. I'm trusting the 22 percent figure more than the
schematic's nominal parts following the measurements from the Lemus docs.

## Engine law

The cutoff parameter is a log position from 0 to 55296. Position 0 is 3.5 Hz
and position 55296 is 12 octaves above, at 14.336 kHz. The filter node turns the
position into the 48 kHz per-stage coefficient with the 257-entry
`p1_filter_g_q16` table in `engine/gen/math_tables.h`, interpolated between
entries. The top entry is clamped at 55296, which is the highest coefficient the feedback
loop takes without parasitic oscillation, so the top pole sits at about
14.18 kHz.

The table is generated by `tools/gen_math_tables.py`. The interpolation error is
below 4 cents above 50 Hz and about 10 cents at 20 Hz. At the 3.5 Hz bottom the
relative error is larger, but inaudible and below the panel's resolution. The table has
257 entries because one entry per 1/256 of the range keeps the linear interpolation
below a cent in the musical range. The top entry is clamped at 55296 because above that point
the feedback loop breaks into parasitic oscillation above, i.e. unmanageable screeching.

## Resonance

The resonance parameter stays on its 0 to 41942 range and is linear. The node
derives `res_k = res / 41942 * 6.25` in Q16. The four-pole loop reaches unity at
about 79 percent of the travel, inside the reference's 0.79 to 0.82 window, and
the cubic clip on the feedback path bounds the self-oscillation.

The ladder drops the passband by `1/(1 + res_k)`. The real SH-101 puts part of
that back into the filter output: R130 from OUT4 and R132 from TR26's emitter sum
into C53 and the VCA, so the output is `(1 + a) * OUT4 / 152` where `a` is the
resonance wiper. The passband at `a = 0.75` is -8.8 dB with the sum and -13.7 dB
without.

The engine's `comp` is 0 to 100 percent of the `1 + res_k` makeup and clamps
negative values to 0. I've set the default at 22 percent (raw 7209), which gives -8.95 dB
at 75 percent and -9.69 dB at 100 percent in the ladder, matching the SH101 reference's measured passband.
The control is not on the Type P panel because it's not something I feel users are going to need, but it stays in the module for future synths and host automation.

I'd originally set the comp to zero because I wanted
the ladder's bass loss, but I found out reading the Lemus reference that the SH-101
brings part of it back at the output, rather than the input.

## Input saturation

The filter input passes through `p1_soft_clip`, `y = x - x^5/8` with `x` clamped
at full scale. The fifth-order term is 0.2 percent at -12 dBFS, 2.5 percent at
-3 dBFS and 12.5 percent at 0 dBFS. Normal levels stay clean and hot mix levels
compres like the OTA input pair. The feedback clip stays separate, so the
self-oscillation amplitude does not follow the input level.

I measured the knee at -12, -6, -3 and 0 dBFS, and the -12 dBFS figure is at the
integer floor, which is intended behaviour, i.e. hot inputs clip, normal inputs don't.

## Envelope depth

`fenv_depth` is now a 0 to 8 octave range, Q16 of the range. The envelope
value is doubled to Q16, scaled by the depth, multiplied by 8 and added to the
log position. The panel now shows the value in octaves, instead of a percentage of the old coefficient
range.

## Migration

The old cutoff was a coefficient in 0 to 55296, scaled by 60211/65536 to keep
the old 44.1 kHz cutoff in hertz. Saved values are mapped through the old
one-pole frequency and then into the new log position, so an old patch keeps its
cutoff. It'd be worth it to test the conversion properly, because an old patch that loads with the right cutoff but the wrong resonance might be hard to notice. The preset record, the plugin state
and the web library have all been version bumped, and convert older patches on load. The migration
test builds a version 6 record with the old 8000 default to prove it all works.
Host automation lanes have no version, so their raw values just shift.

## Limits

The resonance peak shape, the exact self-oscillation spectrum and the compression above
10 kHz are only approximations. The input knee is fixed rather than a drive control, and
the key follow still uses the generic proportional push, so 100 percent does not
track the keyboard at exactly one real octave per keyboard octave.
